# FoolsMate — TryHackMe Write-up

## 1. Reconnaissance

I started with an Nmap scan:

```bash
nmap -sC -sV 10.114.132.128
```

The scan revealed two open ports:

- `22/tcp` — SSH
- `80/tcp` — HTTP

## 2. Web Enumeration

I opened the website and found a chessboard puzzle where the objective was to deliver checkmate in one move.

However, when I attempted to make the winning move through the website, an alert appeared and the move was blocked.

This suggested that the application might be validating moves on the client side.

## 3. Intercepting Requests with Burp Suite

I opened Burp Suite and examined the HTTP traffic generated by the chessboard.

When attempting the blocked move, no corresponding `POST` request appeared in Burp Suite. This indicated that the move was likely rejected by the client-side logic before a request was sent to the server.

I then made a valid chess move to capture an example of the application's API request.

The request was sent to:

```http
POST /api/move HTTP/1.1
Host: 10.114.132.128
Content-Type: application/json
```

The request body contained the starting and destination squares:

```json
{"from":"f2","to":"f3"}
```

## 4. Bypassing Client-Side Validation

I sent the captured request to Burp Suite Repeater.

Since Repeater allows HTTP requests to be modified and sent directly, I could interact with the API without relying on the website's client-side move validation.

I used the captured request as a template and sent it through Repeater.

The server returned a response containing the flag.

## 5. Lessons Learned

- Client-side validation can prevent actions in the browser without sending a request to the server.
- Burp Suite can be used to inspect and replay HTTP requests.
- Repeater allows manual interaction with an application's API.
- Client-side restrictions should not be treated as a security boundary. Servers must independently validate requests and enforce the application's rules.
